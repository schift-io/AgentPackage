# 실제 제출본 앞부분 작성 스타일 레퍼런스

이 레퍼런스는 내부 제출본 샘플의 사업계획서 본문 1-15페이지와 첨부/증빙
16-26페이지에서 확인한 작성 패터만 추출한다. 개인 연락처, 등록번호, 신분증,
서명, 상세 식별값은 재사용하지 않는다. 목적은 지원사업 APM이 사용자 자료를
받을 때 "무엇을 어떤 기조와 도식으로 사업계획서에 옮길지"를 흔들리지 않게
만드는 것이다.

> **예시 일반화 주의:** 본 문서의 예시(Schift, RAG/OCR, 3명, ISO 27001 등)는
> 형식과 문체를 보여주기 위한 것이다. 실제 출력에서는 사용자 회사의 제품명,
> 실제 데이터, 조직 규모로 대체한다.

## 1. 앞부분의 역할

앞부분은 설명서가 아니라 심사자용 압축본이다.

1. 신청서/요약 1-3페이지에서 회사, 아이템, 목표, 시장, 준비 정도, GTM, 이미지가
   한 번에 잡혀야 한다.
2. 팀 구성은 사람 소개가 아니라 왜 이 팀이 이 과제를 수행할 수 있는지의 이력
   증거로 쓴다.
3. 본문은 PSST 순서로 내려간다. 문제인식, 실현가능성, 성장전략, 팀/자금/일정이
   따로 놀지 않고 같은 아이템 서사를 반복 강화해야 한다.
4. 페이지마다 최소 하나의 표 또는 도식이 있어야 한다. 긴 문단만 이어지면 제출본
   밀도가 낮아진다.

## 2. 페이지별 작성 기능

| 위치 | 기능 | 작성 기조 |
| --- | --- | --- |
| 신청서 첫 장 | 회사 기본정보, 분야, 사업기간 목표 | 판단에 필요한 사실만 짧게 쓴다. 목표는 3개 이내로 압축한다. |
| 사업개요 요약 | 아이템 한 줄 정의, 핵심 고객, 배경, 해결 방안 | 첫 문장은 제품 카테고리와 고객 결과를 함께 말한다. |
| 요약 후반 | 준비 정도, GTM, 수익모델, 대표 이미지 | 표로 준비 상태와 사업화 경로를 먼저 보여준다. |
| 팀 구성 | 대표/팀 이력, 수상/선정/제품화 경로 | 연표 나열보다 현재 아이템을 수행할 근거로 연결한다. |
| 지원 동기 | 지역/기관/실증/후속 성장 연결 | "지원받고 싶다"가 아니라 사업 목적과 활용 계획을 맞춘다. |
| 문제인식 | 고객 업무 병목, 기존 대안 한계, 시장 필요 | 문제를 2-3개 카드로 쪼개고 각 문제를 고객 업무 언어로 쓴다. |
| 시장 분석 | 1차/2차 고객, TAM/SAM/SOM, 초기 시장 | 출처 있는 숫자만 쓰고, 초기 진입 시장은 좁게 잡는다. |
| 실현가능성 | 제품 흐름, 경쟁 대안, 차별성, 기술 지표 | 입력-처리-출력 흐름과 비교표를 같이 둔다. |
| 성장전략 | 수익모델, GTM, 기관 패키지, 매출 로드맵 | 가격/채널/이해관계자 가치/매출 가정을 표로 분리한다. |
| 일정/자금 | 사업화 목표, 전체 일정, 협약기간 과제, 투자금/사업비 사용 | 단계별 일정과 예산 산출근거를 분리하고, 지원금 항목은 금액/비율 근거를 명확히 둔다. |
| 기타/지역연계 | ESG, 사회적 기여, 지역 실증, 사업비 사용계획 | 공공사업 목적과 지역/사회적 효과를 별도 절로 연결한다. |
| 증빙 목록 | 필수/해당 시 제출서류, 동의서, 신분/사업자/법인 증빙 | 증빙의 존재와 제출 상태만 요약하고 민감정보를 전사하지 않는다. |

## 3. 문체

- 기본 문체는 제출체와 개조식이다. `검토했습니다`, `생각합니다`보다
  `확보`, `제공`, `전환`, `구축`, `진입`, `확장`처럼 점수화 가능한 명사형과 동사를 쓴다.
- 문단은 `❍` 큰 주장, `―` 근거/세부, `①②③` 순서 또는 유형으로 나눈다.
- 한 항목은 먼저 결론을 쓰고, 다음 줄에서 근거를 붙인다.
- 형용사는 적게 쓴다. `혁신적`, `최고`, `강력한`보다 고객 문제, 현재 대안 한계,
  보유 근거, 실행 방법을 쓴다.
- 표 안에서는 완전한 문장보다 짧은 명사구를 우선한다.
- 확정 근거가 없는 숫자, 고객 수, 인증, 매출, 성능 수치는 쓰지 않는다. 필요한 경우
  `제출 전 확인`으로 낮춘다.

## 4. 섹션별 작성법

### 사업개요 요약

첫 줄은 아래 구조로 쓴다.

`[고객]을 위한 [제품 카테고리], [제품명]`

그 아래 한 줄은 고객이 얻는 결과를 쓴다.

`[고객 자료/업무]를 [처리 흐름]으로 전환하여 [답변/자동화/검토]가 가능한 [서비스]`

요약 페이지는 본문을 축약하지 말고 심사자의 첫 판단을 만든다. 반드시 포함할 항목은
아이템 개요, 배경 및 필요성, 준비 정도, 목표시장/GTM, 수익모델, 대표 이미지다.

**도식 초안 예시 (이해관계자 가치 흐름)**

```
[기관/지원사업] -- 공고/자금/네트워크 --> [자사 스타트업]
                                    |
                                    v
[참여기업/고객] <-- [사용자 제품/서비스가 제공하는 가치] -- [자사 스타트업]
                                    |
                                    v
[기관/지원사업] <-- 성과보고/후속연계 -- [자사 스타트업]
```

### 문제인식

문제는 고객 업무 병목으로 시작한다. 기술 설명부터 시작하지 않는다.

권장 구조:

1. 고객이 하고 싶은 일.
2. 현재 막히는 지점.
3. 기존 대안의 한계.
4. 공고 목적과 연결되는 필요성.

문제 도식은 3개 카드가 적합하다. 예: `업무 병목 A`, `기존 대안 한계 B`,
`운영/비용 부담 C`처럼 문제를 짧은 라벨로 나누고, 각 카드에 고객이 보는 실패 상태를
붙인다.

**도식 초안 예시 (문제 3분할 카드)**

```
┌─────────────┬─────────────┬─────────────┐
│ 문제 1      │ 문제 2      │ 문제 3      │
├─────────────┼─────────────┼─────────────┤
│ 고객이 겪는 │ 기존 대안의 │ 운영/비용   │
│ 구체적 병목 │ 한계        │ 부담        │
└─────────────┴─────────────┴─────────────┘
```

### 실현가능성

실현가능성은 기능 목록이 아니라 작동 흐름과 보유 근거다.

권장 구조:

1. 입력 자료.
2. 처리 단계.
3. 사용자 결과물.
4. 품질 검증 또는 측정 계획.
5. 경쟁 대안 대비 공략 지점.

제품 흐름 도식은 `Input -> Processing -> Output -> Feedback loop` 형태로 만든다.
경쟁 비교는 대안별 한계와 자사의 공략 지점을 같은 행에 둔다.

**도식 초안 예시 (입력-처리-출력 흐름)**

```
[입력 자료/데이터 소스] -> [수집/정제 단계] -> [구조화된 데이터]
                                            |
[회사 자료] -> [분석/추출] -> [회사 근거]
                                            |
                                            v
                              [핵심 처리/가치 창출 단계]
                                            |
                                            v
                              [출력/산출물/후속 액션]
```

### 성장전략

성장전략은 매출 희망이 아니라 시장 진입 경로다.

권장 구조:

1. 현재 수익모델 또는 가격 구조.
2. 이미 확인된 매출/PoC/사용 근거.
3. GTM 채널별 실행 전략.
4. 기관/파트너 패키지.
5. 3개년 매출 또는 성과 로드맵.

가격, 실적, 추정 매출은 한 문단에 섞지 않는다. 각각 별도 표로 분리한다.

**표 예시 (GTM 채널 표)**

| 채널 | 초기 접근 | 확장 방식 | 확인 필요 |
| --- | --- | --- | --- |
| PLG/셀프서비스 | 초기 사용자 직접 사용 | 제품 기반 확장 | 가격 정책 |
| 기관 파트너십 | 지원사업/협회 연계 | 공동 파일럿/홍보 | 협약 조건 |
| Inside Sales | 영업 인력 기준 콜드 outreach | 영업 프로세스 문서화 | 영업 계획 |

### 팀 구성

팀 구성은 자기소개가 아니라 수행 역량 증거이다.

권장 구조:

1. 대표/핵심 인력의 담당 역할.
2. 과거 제품/수상/선정/운영 경험.
3. 그 경험이 현재 아이템으로 이어진 경로.
4. 부족한 역할 또는 채용 계획은 확인 필요로 둔다.

임직원 수만 보고 역할별 인원을 추정하지 않는다.

**표 예시 (팀/회사 근거표)**

| 구분 | 보유 근거 | 사업계획서 반영 문장 | 확인 필요 |
| --- | --- | --- | --- |
| 대표 | 회사 설립/운영 경험 | 회사 운영 및 전략 수행 | 세부 역할 |
| 개발 총괄 | AI/소프트웨어 개발 총괄 | 핵심 기술 및 제품 개발 | 직무 경력 |
| 기획/영업 | 사업 기획 및 고객 발굴 | GTM 및 기관 파트너십 설계 | 영업 파이프라인 |

## 5. 도식 패턴

APM은 사업계획서 초안에 아래 도식 중 필요한 것을 `도식 초안`으로 제안한다. 실제
이미지를 만들 수 없는 출력에서는 표, Mermaid, 또는 HWP 제작 지시문으로 남긴다.
HTML 아티팩트로 렌더링할 때는 `<pre>`, `<ul>`, `<ol>`, `<table>`로 구조화한다.

| 도식 | 쓸 위치 | 구성 |
| --- | --- | --- |
| 이해관계자 가치 흐름 | 요약, 기관 패키지 | 기관, 사용자/참여기업, 자사 3자 구조와 각자 획득 가치 |
| 제품 파이프라인 | 요약, 실현가능성 | 업로드/수집 -> 처리 -> 검색/생성 -> 결과/API/대시보드 |
| 문제 3분할 카드 | 문제인식 | 고객이 체감하는 문제 3개와 실패 상태 |
| 직접 구축 vs 제품 사용 비교 | 문제인식, 차별성 | 시간, 비용, 인력, 운영 부담을 좌우 비교 |
| TAM/SAM/SOM | 시장 분석 | 큰 시장, 직접 접근 시장, 초기 점유 목표를 동심원으로 표현 |
| 입력-처리-출력 흐름 | 실현가능성 | 자료 입력, 핵심 처리 단계, 사용자 산출물, 품질 개선 루프 |
| 경쟁 포지셔닝 2축 | 차별성 | 단순 기능-업무 내장/API형, 운영 전담 낮음-높음 같은 축 |
| 경쟁자 비교표 | 차별성 | 비교항목, 자사, 대안 2-3개, 한계/우위 |
| GTM 채널 표 | 성장전략 | PLG, Inside Sales, 기관 파트너십, 파트너십, Enterprise Sales |
| 기관 패키지 표 | 성장전략 | 패키지명, 구성, 제휴가, 역할 |
| 이해관계자 가치 표 | 성장전략 | 주체, 획득 가치, 성과 |
| 누적 막대 로드맵 | 일정/매출 | 연도별 매출/성과 구분과 주요 전환점 |
| 사업화 목표 표 | 성장전략 | 목표, 내용, 세부 사항 |
| 전체 단계 일정표 | 일정 | 추진 내용, 추진 기간, 세부 내용 |
| 협약기간 월별 과제표 | 일정 | 월, 추진 내용, 산출물, 달성 방안 |
| 투자금/지원금 사용계획표 | 자금운용 | 연차, 비목, 세부 내용, 금액, 산출근거 |
| ESG/지역연계 근거표 | 기타/공공성 | 환경, 사회, 지배구조, 지역 연계 실행 프로그램 |
| 증빙 제출 체크리스트 | 제출 전 확인 | 필수/해당 시, 서류명, 첨부 번호, 상태, 민감정보 처리 |

## 6. 페이지별 도식/표 인벤토리

APM은 아래 인벤토리를 실제 제출본의 도식 문법으로 사용한다. 출력에서 이미지를 직접
생성하지 않는 경우에도 `도식 초안`으로 라벨, 행/열, 축, 노드, 화살표를 구체화한다.
HTML 아티팩트에서는 `<pre>` 블록이나 `<table>`로 동일 구조를 유지한다.

| 페이지 | 패턴 | 쓰임 | APM 반영 |
| --- | --- | --- | --- |
| 1 | 공식 신청서형 표 | 회사 기본정보와 사업기간 목표를 압축 | 신청자/회사 조건은 정부 양식형 grid로 정리하되 개인정보는 최소화 |
| 2 | 좌측 회색 라벨형 요약 표 | 아이템 개요, 고객, 배경, 해결 방안 압축 | 사업개요 요약은 섹션 라벨 -> 근거 불릿 구조로 작성 |
| 3 | 준비 정도/GTM/수익모델 표 + 제품 도식 2개 | 제품 준비, 진입 전략, BM, 시각 증거 | 전략 claim마다 표 또는 작은 구조/프로세스 도식 1개 이상 배치 |
| 4 | 팀 구성 표 | 수행 가능성 증명 | 역할-역량-근거 matrix로 바꾸고 연락처/생년월일 등은 전사 금지 |
| 5 | 창업아이템 개요 표 | 사업 형태, 업태/종목, 핵심 기능 정의 | 상세계획 도입부에 what/who/value 표를 먼저 둔다 |

## 7. HTML 아티팩트 변환 규칙

최종 산출물이 HTML로 렌더링될 때 아래 규칙을 적용한다.

- 표는 `<table>`로, 헤더는 `<thead>`/`<th>`로, 셀은 `<td>`로 작성한다.
- 도식 초안은 `<pre>` 안에 ASCII/유니코드 박스 문자로 구조를 유지한다.
- 순서 리스트는 `<ol>`, 비순서 리스트는 `<ul>`을 사용한다.
- 섹션 제목은 `<h2>`~`<h4>`, 본문 단락은 `<p>`로 구분한다.
- 공식 링크는 `<a href="...">`로, 출처 상태는 링크 옆에 텍스트로 표기한다.
- PDF/HWP 변환은 제출 전 사람 확인 단계로 넘긴다.

## 8. 첨부/증빙 처리 규칙

- 증빙 페이지는 사업계획서 본문 claim을 만드는 자료가 아니라 제출 완결성 점검 자료다.
- 신분증, 법인/사업자 번호, 주소, 서명, 연락처, 생년월일은 기본적으로 전사하지 않는다.
- APM 출력에는 `증빙 종류`, `필수/해당 시`, `제출 상태`, `추가 확인 필요`만 남긴다.
- 빈 기타 증빙 cover page가 있으면 내용을 발명하지 않는다.
- 사업계획서 본문에 증빙을 연결할 때는 "회사 근거: 기존 사업계획서/IR/증빙 파일 확인"
  수준으로 쓰고, 민감 식별값을 근거 문장에 넣지 않는다.

## 11. APM 작성 체크

사업계획서 초안 작성 후 아래를 확인한다.

- 첫 3페이지 역할을 하는 요약이 있는가.
- 각 섹션의 첫 문장이 고객 문제 또는 심사 판단 기준으로 시작하는가.
- 5-0~5-4 각 하위 절에 최소 하나의 표 또는 도식 초안이 있는가.
- 도식 라벨이 고객 언어로 되어 있는가. 낮부 구현명과 도구명만 보이면 실패다.
- 숫자와 실적이 사용자 자료 또는 공식 출처에 묶여 있는가.
- 근거 없는 항목은 본문에 과장하지 않고 제출 전 확인사항으로 날아갔는가.
- HTML 아티팩트에서 표와 도식 초안이 브라우저에서 깨지지 않는가.
- 양식 제공 시: 양식의 섹션 제목과 순서를 그대로 따랐는가.
- 양식 제공 시: 신청서 필드를 company_profile_sources(RAG)로 채웠는가.
