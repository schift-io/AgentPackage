# 제출용 문서 작성 (Submission Writer)

> 핵심 명제: **이건 "내가 사용자에게 보고하는 글"이 아니라, "심사위원·투자자가 점수 매기는 제출물"이다.**
> 보고체·요약 라벨·AI slop을 전부 걷어내고, 평가자가 알고 싶은 사실·수치·근거만 남긴다.

이 스킬은 실제 사용 중 반복해서 깨진 실수들을 규칙으로 박아둔 것이다. 아래를 어기면 다시 깨진다.

---

## 0. 절대 1원칙 — 보고체 금지 (가장 많이 틀리는 것)

불릿/문장은 **"우리가 무엇을 했다/할 것이다"라는 행위·과정 서술(메타)** 이 아니라,
**평가자가 알고 싶은 내용 그 자체(사실/주장/수치/방법)** 를 적는다.

| ❌ 보고체(나한테 보고할 때 쓰는 말투) | ✅ 제출체(사업계획서 알맹이) |
|---|---|
| 시장 규모 산정 기준을 분리함 | TAM 국내 제조업 633,182개 / SAM 식품·음료 9,317개 / SOM 36개월 100~200개 계정(연 3.6~72억) |
| 겐츠베이커리 실증 채널을 확보함 | 겐츠베이커리(부산 다지점 베이커리)와 AX PoC 약 1억원 계약 체결 — 6개월 내 파일럿 매장 즉시 투입 |
| 핵심 연결 흐름을 검증함 | 모임통장 소비신호 → 방문수요 예측 → 발주·인력·메뉴 추천까지 1개 PoC로 검증 |
| KPI는 반복 사용과 적용 효과를 함께 증명함 | 참여 30개사·MAU 20개사·월 리포트 60건·열람률 70% |
| 차별성은 실행 구조에 있음 | 경쟁툴은 분석에서 멈춤 / 본 서비스는 발주·재고·인력까지 실행(W2A) |
| 데이터 제공 범위는 단계적으로 설계함 | 1차: 집계형(지역·업종 수요지수) / 2차: 매장식별형(허용 시 정밀화) |

**금지 동사 패턴(상위 불릿 말미)**: `~를 검증함 / 확보함 / 제시함 / 분리함 / 구성함 / 설계함 / 추진함 / 운영함 / 마련함`,
그리고 `"핵심 ~는 ~임"`, `"~ 중심으로 설계함"` 같은 요약 라벨. → 이런 게 보이면 그 불릿엔 알맹이가 없는 것이다. 사실/수치로 다시 쓴다.

자가 점검: **불릿 하나를 읽고 "그래서 뭐?"가 나오면 실패.** 숫자·고유명사·구체 방법이 들어가야 한다.

## 1. Slop 블랙리스트 (말투·패턴)

작성·교정 시 아래를 모두 제거한다.

- **AI 과장어**: 혁신적, 압도적, 독보적, 최첨단, 완벽한, 극대화, "~뿐만 아니라 ~까지", "단순한 ~가 아니라".
- **공허한 요약 라벨**: 위 0절의 메타 불릿. 상위 불릿이 하위 불릿의 제목 노릇만 하면 삭제하고 하위를 끌어올린다.
- **메타 안내문**: "본 계획서는 평가자가 ~ 읽도록 작성함" 같은 문서 사용설명. 전부 삭제.
- **비장·과몰입 톤**: 사활을 걸고, 총력, 반드시 성공, 모든 것을 쏟아, "목숨 건 듯한" 표현. 차분한 근거 제시로.
- **반복**: 같은 주장(예: 3주체가 각자 얻는 것)을 장마다 재서술하지 않는다. 1회 표로 정리.
- **합니다체**: 정부 개조식은 `~함/~음` 또는 명사형 종결(`구축함`, `제공`, `~ 가능`). "합니다/입니다" 금지.

## 2. 구조 규칙 (양식 정합)

- **계층은 2단계까지만**: 대분류(`1.`, `2.` … = h2) / 중분류(`3-1)`, `3-2)` … = h3). 그 아래는 **헤딩이 아니라 개조식 불릿**.
  - 소제목이 더 필요하면 헤딩(h4) 대신 `□ 라벨` 굵은 글씨로 둔다(계층 추가 아님).
- **개조식 2층 불릿**: 상위 `○`(핵심 한 줄, 대략 40자 이내) → 하위 `-`(상세). 상위가 길어지면 안 된다.
- **wall-of-text 금지**: 120자(약 3줄) 넘는 서술 문단 금지. 쪼개서 불릿으로.
- **표 활용**: 비교/수치/항목 정리는 문단 대신 표. (AS-IS·TO-BE, KPI, 시장규모, 사업비, 리스크 대응 등)
- **다이어그램**: 핵심 흐름 1개당 그림 1개(과하지 않게). 제출이 docx면 인라인 SVG 말고 PNG로.
- **첫 hierarchy(대분류 제목) 간결**: 제목은 짧게. 긴 건 양식이 강제하는 문서 표제만 허용.

## 3. 내용 규칙 (점수를 만드는 것)

1. **공고문·양식부터 리서치**: 제출 전에 (a)양식의 항목 구조 (b)각 항목 ※안내문이 요구하는 포함요소
   (c)평가기준/배점을 추출해 항목별로 매핑한다. 양식에 없는 계층·항목을 임의 추가하지 않는다.
2. **평가기준 역산**: 배점 항목마다 대응 근거(문제정의 명확성, 데이터 활용, 기술 타당성, 구현 가능성, 시장성,
   실증, 현장 적용성, 성과, 리스크, 사업화, 사업비)를 빠짐없이 채운다.
3. **실데이터·출처**: 수치는 1차 자료(매출장·실태조사·내부 지표)에서. 출처 명시. **추정·기억으로 숫자 만들지 않는다.**
   - 과대계상 금지: 반제/취소/중복 항목 제외하고 순액으로. (예: 매출장의 반제 건은 빼고 누계 공급가액 사용)
   - 불확실은 `확인 필요`로 명시(생년월일·연락처·미확정 인증/IP 등).
4. **정직성 가드레일**: 미입증 성과는 `확정`이 아니라 `측정 예정(evidence gate)`. 전환율·정확도 목표를 확정값처럼 쓰지 않는다.
   인증(ISO/GS 등)은 "취득 확정"이 아니라 "준비·사전진단·시험평가 준비". 규제(개인정보·금융 등) caveat 포함.
5. **사용자가 빼라는 건 뺀다**: 제외 지시(예: 특정 수상/이력) 철저히 반영.
6. **과제 적합성 정중앙화**: 자사 강점을 '변방 확장'이 아니라 '공고 과제의 핵심 요구'와 직접 일치시켜 배치.

## 4. 출력(특히 docx 제출) 규칙

- docx에 넣을 HTML은 Word 친화로: `맑은 고딕` 11pt, 테두리 있는 표(th 음영), 단순 CSS.
- 인라인 SVG는 Word에서 안 깨지게 PNG로 변환해 삽입(base64 임베드 권장). figcaption 부여.
- 내부 메모(제출 전 TODO, 작성 가이드)는 제출본에서 제거.
- 과제명 등은 설명형이라 길어도 되지만, 일반 소제목은 짧게.

## 4.5 표준 양식·개조식 규격 (실제 합격 사업계획서 기준)

### 양식 프레임 — 대부분의 정부지원사업 = PSST + 부속
- 부속: 일반현황 / (창업)기업·팀 구성 현황 / 지원동기·활용계획 / 아이템 개요
- **1. 문제인식 (Problem)** — 배경·필요성, 목표시장·고객 분석
- **2. 실현가능성 (Solution)** — 현황·준비정도, 구체화 방안, 경쟁·차별성
- **3. 성장전략 (Scale-up)** — BM·사업화, GTM, 자금·매출 계획, 추진 일정
- **4. 팀 구성 (Team)** — 대표·팀원 역량, 채용·외부 협력
- ※ 공고마다 항목명이 다르니 실제 양식의 ※안내문을 그대로 따른다. 그 ※안내문 자체는 제출본에서 삭제한다.

### 계층·마커 (이 표기를 쓴다)
- 대제목: `1. 문제인식 (Problem)` (번호 + 한글 + 영문 프레임명)
- 중제목: 굵게/밑줄 한 줄 (예: "창업아이템 배경 및 필요성")
- 상위 항목: `❍` (간결한 토픽 또는 한 줄 핵심 주장)
- 하위 상세: `―` (반드시 수치·고유명사·방법 포함)
- 열거: `①②③④`
- → 2계층(❍/―) 유지. ❍가 토픽 라벨이어도 되나, 그 아래 ―는 전부 구체적이어야 함(라벨만 있고 알맹이 없으면 0절 위반).

### 강한 제출문은 "표"로 말한다 (아래는 거의 필수)
| 표 | 컬럼 예시 |
|---|---|
| 목표 고객 | 구분(1차/2차) / 대상 / 고객 문제 |
| 경쟁 환경 | 대안 / 한계 / 자사 공략 지점 |
| 경쟁사 비교 | 비교항목 × 경쟁사 (O·X·수치 — **자사 약점도 X로 정직 표기**) |
| 기술 차별성 | 지표 / 수치 / **의미(왜 중요한지)** — 예: R@10 95%, p99 502us, "Qdrant 대비 8.7배" |
| 수익 모델 | 모델 / 내용(가격) |
| 매출 실적·추정 | 순번 / 고객 / 제품 / 시기 / 수량 / 가격 / 금액 |
| 3개년 매출 | 구분 × 연도 + 합계 |
| 추진 일정 | 순번 / 추진 내용 / 기간 / 세부 내용 (전체 + 협약기간 2종) |
| GTM | 채널(PLG/Inside Sales/기관/Enterprise) / 진입 전략 |

### 수치·출처 규칙
- 모든 주장에 수치 또는 출처. 시장 규모는 named 기관 인용(예: "Grand View Research, RAG 시장 2024 12억$→2030 110억$").
- 외부 근거는 **각주 `1)2)`** 로 달고 하단에 출처 명기.
- 기술 지표는 벤치마크 수치 + "의미" 한 줄. 못 가진 것은 Schift RAG/source memory에서 먼저 보강하고, 그래도 없으면 최종 본문이 아니라 별도 보완 artifact로 분리한다. 현황은 "'26.5 기준"처럼 시점 명시.

### "또" — 점수 더 받는 디테일
- **정책 부합성**: 공고의 정책목표(지역·고용·수출·약자 등)와 1~2줄 연결(정부사업 가점).
- **고용·자금조달**: 사업비 비목별 산출근거 + 자부담/매칭, 채용 계획.
- **분량·양식 준수**: 페이지 제한·폰트·표 형식 지킴. 표/그림에 번호·캡션·출처. 로드맵 그림 1장(과하지 않게).

## 5. 제출 전 Slop 감사 (전달 직전 필수 — grep로 0 확인)

```bash
F=대상.html   # 또는 변환 텍스트
# 보고체/메타 불릿
grep -nE '검증함|확보함|제시함|분리함|구성함|설계함|추진함</li>|핵심 .{0,15}는 .{0,15}임' "$F"
# AI 과장어
grep -nE '혁신적|압도적|독보적|최첨단|완벽한|극대화|뿐만 아니라' "$F"
# 합니다체
grep -nE '합니다|입니다' "$F"
# 금지/이전 라벨 잔존(과제별로 지정)
# wall-of-text(파이썬): 120자+ <p> 개수가 0인지
```
- 위 grep 결과가 **0**이어야 통과. 하나라도 걸리면 그 줄을 사실·수치 기반으로 다시 쓴다.
- 추가 육안 점검: 불릿 무작위 5개를 읽어 "그래서 뭐?"가 안 나오는지. 표·수치·출처·이미지 정상인지. 계층 ≤2단계인지.

### 5.5 Agent Hub 최종 산출 gate

- `초안`, `placeholder`, `TODO`, `확인 필요`는 최종 제출 artifact에 남기지 않는다.
  - 해결 가능한 항목은 Schift RAG/source memory에서 근거를 찾아 본문에 반영한다.
  - 해결 불가능한 항목은 본문이 아니라 별도 operator TODO artifact로 분리한다.
- KPI·사업비·추진일정·시장규모·경쟁비교는 문단으로 뭉개지 말고 표로 작성한다.
- sub-agent 결과를 합친 뒤 reviewer가 아래를 0/1로 판정한다.
  - 공고/양식 필수 절 누락 없음
  - `schift-rag` 근거 사용
  - source memory 사용
  - llm.schift.io Worker/RTX route telemetry 존재
  - token/cost 기록 존재
  - 금지어 grep 0건
  - 표 3개 이상 또는 양식상 필요한 표 전부 존재

## 6. 작업 순서 (codex 외주 병행 가능)

1. 공고문·양식·기존 자료·실데이터(매출장 등) 읽고 항목/평가기준/사실 추출.
2. 항목별 골격 + 사실/수치 매핑(여기서 0~3절 규칙 확정).
3. 본문 작성/교정 — 분량 크면 섹션별로 codex에 위임하되 **반드시 위 SPEC(0~4절)을 프롬프트에 동봉**.
   - codex는 보고체·요약 라벨을 잘 만든다. "메타 불릿 금지, 사실/수치로" 예시를 프롬프트에 박을 것.
4. 재조립 → **5절 slop 감사** → 육안 검수 → 전달.

> 한 줄 요약: **"보고하지 말고, 제출하라."** 모든 불릿이 숫자·고유명사·구체 방법을 담고 있는지로 판정한다.
